# Asymmetric Entropy Capsule Bootstrap

This artifact measures a pre-DTLS bootstrap path for an ESP32 client with no
credited local entropy.

The gateway performs the first randomized cryptographic operation and sends an
authenticated entropy capsule. The ESP32 performs deterministic verification,
decapsulation, HKDF, and `entropy_add_entropy()` before any DTLS session starts.

## Profiles

The default profile uses the post-quantum capsule path:

```text
ESP32 cold boot
  -> connect Wi-Fi
  -> send BOOT_HELLO over UDP
  -> receive ML-KEM-512 capsule signed with ML-DSA-44
  -> verify ML-DSA-44 with the pinned gateway public key
  -> decapsulate ML-KEM-512 with the device bootstrap key
  -> HKDF(shared secret, boot transcript)
  -> entropy_add_entropy() into the Zephyr BLAKE2s pool
```

The Ed25519 beacon profile remains as a development control. It has no
per-device KEM secret. Use it for reachability and timing checks, not as the
main asymmetric capsule claim.

The firmware still contains SRAM startup and timing capture hooks from earlier
experiments. Treat raw dumps from those hooks as lab-only diagnostics.

## Capsule Server

Run the collector before flashing or resetting the ESP32:

```bash
cd entropy-capsule-bootstrap
python3 scripts/generate_pq_keys.py
python3 scripts/collect_teb_boot.py --port /dev/ttyUSB0 --runs 1 \
  --server-bind 0.0.0.0 --server-port 6767 --server-profile pq \
  --log results/capsule_boot.log \
  --server-log results/capsule_server.log
```

The collector builds and starts `server/teb_pq_beacon_server`. The checked-in
ML-KEM-512 and ML-DSA-44 keys are deterministic lab keys generated by
`scripts/generate_pq_keys.py`. Replace them before any deployment experiment.

For the Ed25519 control, build with `--profile ed25519` and collect with
`--server-profile ed25519`. That path uses `server/teb_beacon_server.py`.

The server IP passed to the firmware must be reachable from the ESP32 Wi-Fi
network. If the client sends `BOOT_HELLO` and then times out, check that the
ESP32 and host are on the same reachable network.

## Build and Flash

```bash
cd entropy-capsule-bootstrap
./scripts/build.sh --wifi-ssid "$SSID" --wifi-pass "$PSK" \
  --server-ip 192.168.0.16 --profile pq --clean --flash --monitor
```

For raw startup characterization:

```bash
./scripts/build.sh --wifi-ssid "$SSID" --wifi-pass "$PSK" \
  --server-ip 192.168.0.16 --profile pq --puf-dump --clean --flash --monitor
```

Raw startup dumps can reveal candidate device secrets. Keep them out of public
results unless they have been explicitly sanitized.

## Parse Logs

```bash
python3 scripts/parse_teb_boot_log.py results/capsule_boot.log \
  --server-log results/capsule_server.log \
  --csv results/capsule_boot_runs.csv \
  --summary results/capsule_boot_summary.json
```

To compare the Ed25519 control and PQ capsule profile:

```bash
python3 scripts/compare_teb_boot_profiles.py \
  --ed-log results/ed25519_boot.log \
  --ed-server-log results/ed25519_server.log \
  --pq-log results/pq_capsule_boot.log \
  --pq-server-log results/pq_capsule_server.log \
  --summary results/capsule_profile_comparison.json
```

For raw startup captures:

```bash
python3 scripts/analyze_puf_captures.py logs/startup_captures.txt \
  --raw-bin data/startup_captures.bin \
  --summary results/startup_summary.json \
  --csv results/startup_summary.csv \
  --distances-csv results/startup_pairwise_distances.csv
```
